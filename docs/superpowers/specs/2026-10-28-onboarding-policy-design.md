# Configurable onboarding

Approved conversation: controls for ID capture, passkeys and password use Required / Optional / Disabled. Password placement is With email / After email verification / Hidden. Defaults: required ID, required passkey, disabled hidden password.

Extend the existing revisioned per-environment runtime document with `onboarding`: `idCapture`, `passkey`, `password` requirements (`required`, `optional`, `disabled`), `passwordPlacement` (`with_email`, `after_verification`, `hidden`), and `passwordPolicy`: `minLength`, `maxLength`, `lowercase`, `uppercase`, `numbers`, `symbols` (each `allowed`, `required`, `disallowed`). Initial dormant password policy: 12–128 characters, all four classes allowed. Supported character domain is ASCII letters, digits and printable ASCII punctuation (no whitespace). 8–128 length bounds, min <= max, at least one enabled class. Disabled password iff hidden placement. Reject invalid documents rather than silently weakening requirements.

Schema stays 1 for additive compatibility. Missing onboarding in old documents normalizes to ID optional when old capture boolean true, otherwise disabled; passkey required; password disabled/hidden. New defaults enable required capture. Retain features.idCapture as the compatibility flag derived from onboarding on new publication. Old clients cannot enforce new requirements and must be upgraded.

Reuse runtime history, review and rollback. Server validates password before setting it in Cognito. Entry with email keeps the value only in memory and submits after email verification; process loss/cross-device confirmation asks again after verification. No password in proofs, URLs, saved state or logs. Email OTP stays available for recovery. Disabled means onboarding omitted, not revocation of existing credentials. Password login for previously enrolled users stays usable regardless of later enrollment policy.

POST /auth/password/set accepts bearer access token, {password}, returns {password_registered:true}. POST /auth/password/start accepts {email}; POST /auth/password/complete accepts {email,session,password}, following Cognito USER_AUTH PASSWORD challenge. POST /auth/status returns passkey_registered, password_registered, id_captured, onboarding_complete. Server computes completion against current requirements and durable enrollment facts. An authenticated session alone does not mean onboarding complete. Ready server capture satisfies capture; capture/parsing never asserts identity verification.

Android passes validated runtime policy into host, routes unmet required steps, permits optional skips, omits disabled steps, and refreshes authoritative status after enrollment/capture. Cancel/back from capture never counts as success. When settings are unavailable, block new onboarding completion and provide retry. Existing local deferred flags cannot bypass required steps.

Approach: extend existing configuration and flow rather than invent a separate policy service or hardcode dashboard-only visibility. Keep Cognito as password credential owner. Deploy backend and Android together; do not change running environment settings or deploy in this task.
